# The Context-Base: Waihona

**Status:** draft
**Issue:** [#5](https://github.com/bjamba/kamaaina/issues/5)
**Author(s):** bjamba, with frontier assistance (Class 1 feeding Class 2)

> **Naming (proposed, pending review):** *waihona* — depository, archive, a place where valuables are kept (as in *hale waihona puke*, library). Proposed for the context-base format and its scaffold tool; see [docs/naming.md](../../docs/naming.md). Corrections from speakers of ʻōlelo Hawaiʻi welcome.

## Problem

Pattern 2 of the [context engineering catalog](../../docs/patterns/context-engineering.md) — external memory a small model can traverse — is mandatory at Tiers 1–2, which means nearly every Kamaʻāina tool depends on it. Until now it has been a prose sketch. Without a concrete format: every tool invents its own state layout, tools cannot share memory, and "the model traverses an index" is a hope rather than a procedure a 7B model reliably executes.

This document is the reference design: the on-disk format, the sizing rules that keep every read within budget, the traversal protocol written as instructions a small model follows, the write path, and the interface Kū uses when designing skills around it.

## Constraints

- **Tier 1 is the floor.** Every individual read during traversal — an index or a leaf — must fit comfortably in an 8k-window session alongside a task. Sizing rules below are derived from this, not chosen aesthetically.
- **Deterministic maintenance.** Indexing, size enforcement, and structure checks are script work (`not_ai`). A model never counts tokens or rebuilds an index.
- **Plain files, zero dependencies.** Markdown on disk, Python stdlib for the scripts, no database, no embeddings. A human can read and repair a waihona with a text editor — Principle 3.
- **Offline always.** `network: none`; nothing in the format references anything not on disk.

## Design

### On-disk layout

```
<base-root>/                  # global: ~/.kamaaina/context-base/   project: ./context-base/
├── INDEX.md                  # root index — the only guaranteed entry point
├── _inbox.md                 # write-path staging (never read as authority)
├── <branch>/                 # a topic directory
│   ├── INDEX.md
│   ├── <leaf>.md             # a fact file, sized to budget
│   └── <sub-branch>/
│       ├── INDEX.md
│       └── <leaf>.md
```

- Names are ASCII slugs (naming rule); proper orthography lives inside the files.
- Depth is soft-capped at 3 levels below root. Deeper nesting means traversal reads too many indexes before touching a fact.
- A directory contains an `INDEX.md` and any mix of leaves and sub-branches.

### Index format

An `INDEX.md` is regenerated by the script from leaf frontmatter and child indexes — hand-edits to entries are overwritten; hand-edits to the purpose line are preserved.

```markdown
# <branch title>
> <one-line purpose of this branch — human-authored, preserved on reindex>

## Branches
- [dgx-spark/](dgx-spark/INDEX.md) — measured limits and quirks of the DGX Spark stack

## Leaves
- [quantization-notes](quantization-notes.md) — Q4 vs Q5 quality/latency tradeoffs observed locally
```

Rules (enforced by `check`):
- One line per entry: `- [slug](path) — description`. **Entry line ≤ 160 characters.** The description *is* the retrieval surface — it must say what a reader would find, not restate the slug.
- **≤ 50 entries per index.** Past that, the branch splits.
- An index stays ≤ ~1,500 tokens total; with the caps above this follows arithmetically.

### Leaf format

```markdown
---
summary: Q4 vs Q5 quality/latency tradeoffs observed locally
updated: 2026-08-08
---
<the fact(s): freeform markdown>
```

- `summary` becomes the index entry description — one line, ≤ 140 chars.
- `updated` is the staleness signal (see below).
- **Body ≤ 1,000 tokens** (default; a base may declare a lower cap for stricter tiers). A leaf is one coherent topic a session loads whole — never a grab-bag.

### Sizing rules and the split procedure

Token counts use the conservative estimator from [context-budget.md](../ku/context-budget.md) (~4 chars/token) unless a real tokenizer is configured.

When `check` flags an oversized leaf or index:
1. **The script flags; it does not split content.** Semantic splitting is judgment — model or human work.
2. The split produces either sibling leaves (same branch) or a new sub-branch with the original slug, each piece getting its own `summary`.
3. `reindex` then rebuilds the affected indexes deterministically.

This is the one place model work enters maintenance, and it is triggered, bounded, and verified by scripts on both sides.

### The traversal protocol

Written to be embedded verbatim (or by reference) in any skill that reads a waihona. This is the load-bearing part of the design — it is a procedure, not a hope:

```
To retrieve from the context-base at <base-root>:
1. Read <base-root>/INDEX.md. Nothing else yet.
2. Choose at most 2 branches whose descriptions match the current task.
   Read only their INDEX.md files.
3. Choose at most 3 leaves total across those branches, by description.
   Read them. These leaves are now your working knowledge.
4. Stop. Do not browse further. Do not read leaves "just in case."
5. If no description matched the task, do not guess: state the gap and
   record it in _inbox.md as a candidate leaf (see write path).
6. If two leaves conflict, prefer the newer `updated`; note the conflict
   in _inbox.md.
```

Worst-case read cost: root index (≤1.5k) + 2 branch indexes (≤3k) + 3 leaves (≤3k) ≈ **7.5k tokens** — the ceiling, hit only when everything is maximal. The typical cost is far lower, and the numbers are why the caps are what they are: the protocol's worst case must survive a Tier 1 session with instructions and a task also in the window (see Tier & budget analysis).

### The write path

New knowledge never edits the tree directly mid-task:

1. **During a session**, candidate facts are *appended* to `_inbox.md`: one block per fact — proposed branch, proposed summary line, body.
2. **Filing** is its own small operation (end of session, or a dedicated pass): each inbox block is placed into an existing leaf (append/merge) or becomes a new leaf; hard cases are left in the inbox with a note rather than mis-filed.
3. `reindex` runs after filing; `check` confirms nothing oversized.

`_inbox.md` is staging, never authority: the traversal protocol does not read it, and `check` warns when the inbox grows stale (many unfiled blocks) — an unfiled inbox is deferred memory-loss.

### Staleness and conflict

- `updated` on every leaf; newer wins at read time (protocol step 6).
- A leaf that *supersedes* another says so in its body ("supersedes: <leaf>, <date>") and the filing pass deletes or rewrites the loser — conflicts get resolved at filing time, not carried forever.
- No locking. A waihona is single-user by design; concurrent writers are out of scope for v0 (open question).

### Interface for Kū and generated skills

When Kū designs a skill that needs persistent memory, it does not invent storage; it declares waihona residency:

- The skill's `state_files` entries point into a base (`~/.kamaaina/context-base/<branch>/…` for durable cross-skill knowledge, `./context-base/…` for project-local), with `lifecycle: persistent`.
- The skill's instructions embed the traversal protocol for reads and the inbox convention for writes — both by reference to short, fixed text blocks so the cost to the skill's instruction budget is bounded (the protocol op file measures ~240 tokens).
- Maintenance is never the skill's job: manifests declare `exec: ["python3 <waihona>/scripts/cb.py …"]` for `reindex`/`check`, and Kū schedules them at checkpoint boundaries.
- Kū's own long-term state (the stack profile, generated-skills record — per the ["eats its own cooking" contract](../ku/overview.md#kū-eats-its-own-cooking)) is the first resident.

## Alternatives considered

- **Vector/embedding retrieval.** Rejected for v0: adds a model dependency and an opaque index to what must stay human-repairable and deterministic (Principles 2–3). Index-descriptions-as-retrieval-surface is weaker at recall but inspectable, and failure is visible (a bad description) rather than silent. Revisit only if the Tier 1 validation shows description-matching genuinely failing.
- **Single JSON state file** (the teach-me `curriculum.json` shape). Works for one tool's structured state, but does not scale to shared, growing knowledge: no partial loading, so the whole file rides in context — exactly the failure the pattern exists to prevent.
- **SQLite.** Durable and queryable, but not model-readable without tooling, not diff-able, not editor-repairable. The filesystem *is* the database here, on purpose.

## Tier & budget analysis

| Read | Cap |
|---|---|
| Any single index | ~1,500 tokens |
| Any single leaf | ~1,000 tokens |
| Protocol worst-case (1 root + 2 branch indexes + 3 leaves) | ~7,500 tokens |
| Traversal protocol text itself (`find.md`, measured) | ~240 tokens |

At Tier 1 (8k–16k usable), the worst case fits only in the 16k half of the range with a task present; the protocol's *typical* case (1 branch, 2 leaves ≈ 4k) fits everywhere. Skills targeting the 8k floor should declare tighter per-base caps (e.g. leaf ≤ 600) — the scaffold's `check` accepts overrides. At Tier 2+ the format is comfortable without adjustment. The scaffold tool itself is `tier.minimum: 1` (its model-facing operations are the protocol and filing — both tiny).

## Validation plan (Tier 1, pending hardware run)

`cb.py fixture` generates a deterministic 3-level base (3 branches × 2 sub-branches × 4 leaves = 24 leaves). The certification run, on a Tier 1-class model (issue #5 acceptance):

1. Query A (single-branch answer), Query B (cross-branch, 2 branches), Query C (no matching leaf — must report the gap, not hallucinate a leaf).
2. Pass = the model reads only protocol-permitted files (transcript-checked), retrieves the right leaves for A and B, and files a gap note for C.
3. Results recorded in this doc's status and as a certification record once #11's format exists.

## Open questions

- Concurrent writers (two sessions, one base): timestamp-suffixed inbox files per session, or explicitly unsupported until it hurts?
- Should the global base root be configurable (`KAMAAINA_HOME`)? Leaning yes, trivial.
- Real-tokenizer integration: worth the optional dependency, or is chars/4 conservative enough until #1's measurements say otherwise?
